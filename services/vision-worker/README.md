# Vision Worker

该服务读取主摄像头实时流，从 API 定期获取所有已发布的摄像头线路定义，并把真实攀爬观察幂等写回业务系统。

运行时只接受用户确认的线路轮廓、起点和终点。Worker 不按线路名称或固定颜色猜测业务 ID；摄像头、墙面或分辨率变化后必须重新确认视觉定义。

`worker-defaults.json` 只保存与具体线路无关的姿态、接触和时序阈值。生产多线路模式的线路 ID、监控区域、岩点轮廓、起点和终点均由 API 动态下发。若要运行旧的单线路离线实验，必须通过 `--calibration` 或 `CAMERA_WORKER_CALIBRATION_PATH` 显式指定包含线路几何的校准文件。

生产部署由仓库根目录的 `infra/deploy-vision-worker.sh` 完成。Worker 使用独立 Compose 项目和受限环境文件，通过主应用内部 Docker 网络访问 API，不开放公网端口。

## 识别录像生命周期

- Worker 只从 API 获取 `PUBLISHED` 线路及其 `PUBLISHED` 版本；停用、删除或未创建的线路不会进入正式识别。
- 起步确认依赖完整姿态序列，因此已发布线路的起点出现双手候选后，视频先写入 `temporary-clips`，并继续绑定同一人物。未匹配任何有效线路时，临时视频和候选分析目录立即删除，不产生业务记录。
- 匹配有效线路后先幂等写入识别记录，再将原片转为无音频、H.264、`faststart` MP4 并流式上传。上传成功后删除 Worker 原片和所有候选标注视频。
- 单次尝试最长 600 秒；上传失败的临时文件保留用于诊断，并由启动及每 5 分钟周期清理在 24 小时后回收。
- API 对普通录像保留 72 小时、待复核录像保留 14 天；改判后延长到 30 天。结构化识别和复核记录不随录像过期删除。

当前 POC 在尝试结束后才确认线路起步，因此仍需要短期候选文件。后续如果把同一套起步状态机前移到实时推理环节，可以进一步做到确认起步后才创建临时录像，不能另写一套判定规则。

## 正式起步门槛

双手靠近起点只会创建临时候选，不再直接形成攀爬记录。正式起步必须由同一人物轨迹在限定时间内同时满足：

- 起点姿态稳定停留；
- 至少一个脚点获得线路支撑；
- 髋部相对起步姿态持续上升；
- 手部推进到起点上方的后续线路岩点。

人物跟踪中断、候选超时或缺少任一证据时立即回到等待状态。未确认起步的录像和分析文件会被删除，不写入 API，也不上传录像。事件中的 `confidence` 是规则证据评分，并非经过真实样本校准的统计正确率。
