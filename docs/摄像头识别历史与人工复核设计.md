# 摄像头识别历史与人工复核设计

> 状态：本地 feature 开发基线，尚未部署 Azure

## 1. 目标

把摄像头页面从“展示少量 Worker 输出”补全为可追溯闭环：算法原始判定不可覆盖，授权员工通过短期录像证据确认、改判或标记无效，最终结论和操作人可审计。

## 2. 记录与查询

- 摄像头首页固定读取最近 10 条真实识别记录，标题为“识别结果”，底部明确提示数量上限。
- 完整历史使用服务端游标分页，避免新数据插入导致页码漂移。
- 线路编号/名称、算法结果、复核状态和日期范围筛选始终展开，不依赖“查看全部”才显示。
- `requiresReview` 只是算法优先级提示；人工状态独立保存为 `UNREVIEWED`、`CONFIRMED`、`OVERRIDDEN` 或 `INVALIDATED`。
- 页面分别展示算法结果、算法评分、最终结论和复核状态。算法评分当前来自规则阈值，不表述为统计正确概率。

## 3. 不可变复核

每次复核追加一条 `CameraObservationReview`：

- `CONFIRM`：确认算法原判；
- `OVERRIDE_COMPLETED`：改判完攀；
- `OVERRIDE_FAILED`：改判失败；
- `INVALIDATE`：不是有效攀爬片段。

改判和标记无效必须填写原因。`ClimbObservation.outcome` 永远保留算法原判；`reviewStatus` 是便于检索的最新状态投影，最终结论取最近一条复核记录。

## 4. 录像证据

录像不写入 PostgreSQL。`CameraObservationEvidence` 只保存对象键、大小、时长、SHA-256、状态和过期时间。访问需要登录权限，API 支持 HTTP Range，并设置私有、不缓存响应。

Worker 只会收到已发布、未停用且完成视觉定义的线路：

1. 人物触发后写短期候选文件，内存环形缓冲补齐起步前画面；
2. 完整姿态分析没有确认任何有效线路起步时，立即删除全部候选文件；
3. 匹配有效线路后写入正式识别记录；
4. 创建不含密钥的待上传恢复记录，将原片转为无音频 H.264 MP4 后上传；
5. 上传最多进行 3 次退避重试，重试耗尽后将业务记录标记为 `FAILED`；
6. 上传成功立即删除恢复记录、Worker 原片和候选标注视频；Worker 重启会恢复未完成任务，无法恢复的异常残留最多保留 24 小时。

`ClimbObservation.evidenceState` 独立记录录像生命周期：`NOT_RECORDED` 表示功能启用前或人工写入的记录，`PENDING` 表示正在处理，`AVAILABLE` 表示可播放，`FAILED` 表示重试后仍失败，`EXPIRED` 表示已按策略销毁。前端必须分别解释这些状态，不得把历史无录像统一描述为 Worker 上传失败。

单次尝试硬上限为 600 秒。超过上限沿用算法结果并进入人工可复核范围，避免异常跟踪导致无限文件。

## 5. 过期策略

| 场景                   | 录像保留时间   |
| ---------------------- | -------------- |
| 普通、未被算法建议复核 | 72 小时        |
| 算法建议复核且尚未处理 | 14 天          |
| 人工确认或标记无效     | 操作后 72 小时 |
| 人工改判               | 操作后 30 天   |

API 启动时及每 15 分钟扫描到期对象。对象删除失败时进入已有清理重试队列；数据库立即标记为 `EXPIRED`，从业务接口拒绝继续播放。视频过期不删除识别结果、算法事件或人工复核记录。

## 6. 当前边界

- 当前按单个 MP4 上传，采用 600 秒和 128 MiB 双重上限；分片上传接口保留为规模化阶段的扩展点。
- 对象仍使用现有私有 MinIO bucket 的机构隔离前缀，后续可以无损迁移到独立 evidence bucket。
- 生产部署、云端 migration、存储容量告警和 Azure 生命周期规则不属于本地开发阶段，必须在用户明确要求上线后单独执行和验证。
